# nowhere-agent 数据治理与个人信息保护合规说明(面向国内部署)

> **适用对象**:将 nowhere-agent 部署于中国境内、面向员工或客户提供 Agent 服务的企业。
> **目的**:说明平台已具备的数据治理与个人信息保护(PIPL《个人信息保护法》)技术能力,并明确部署方仍需自行落实的组织义务。本文是技术事实清单,不是法律意见。
> **基线**:`master` @ `c83247d`(2026-08-11)。

---

## 1. 平台处理的数据与分类

| 数据类别 | 典型内容 | 存储位置 | 是否个人敏感信息(常见认定) |
|---|---|---|---|
| 账号数据 | 邮箱、密码(bcrypt)、姓名、角色 | `users` / `teams` / `memberships` | 邮箱属个人信息 |
| 会话与消息 | 用户与 Agent 的对话、工具调用记录 | `sessions` / `messages` / `run_events` | 对话内容可能含个人信息/敏感信息 |
| 记忆 | 长期记忆、印象、摘要、洞见 | `memories`(含向量列) | 可能含个人信息 |
| 用量与审计 | token 用量、审计事件(actor/ip/ua/动作) | `usage` / `audit_log` | IP 属个人信息(常见认定) |
| 业务数据(可选) | 经 `query_db` 查询的业务库数据 | 业务库(部署方自有) | 依业务而定 |

## 2. 已具备的技术能力(对照 PIPL 核心义务)

### 2.1 告知-同意(App 处理规则的告知)
- 平台**不采集**任何第三方数据:数据仅来自用户本人输入与部署方配置(LLM 调用、业务库查询)。
- 对话内容**不写入审计日志**(`docs/enterprise-readiness-2026-08.md` §2.2 设计约定),审计仅记"谁在何时做了什么"。
- **部署方义务**:向员工/用户公示《隐私政策》,说明对话内容将发送至所配置的大模型厂商(DeepSeek/Qwen/GLM 等)与自建网关。

### 2.2 最小化与目的限制
- `query_db` 只读工具:语句守卫(仅 SELECT/WITH/EXPLAIN/SHOW/VALUES)、READ ONLY 事务、行/列/字节上限、每语句日志 —— Agent 对业务库的访问被限制为"只读 + 限额 + 可审计"(`internal/toolruntime/builtin/querydb.go`)。
- 工具级风险分级 + 人工审批(`internal/permission`):高风险操作默认 ask/deny。
- **部署方义务**:为 `query_db` 配置**独立只读数据库账号**(least-privilege),只授予业务必需表的 SELECT。

### 2.3 个人权利:查阅/复制(导出权, PIPL §45)
- `GET /api/me/export`:用户可导出自己的完整数据足迹(账号、会话、消息、记忆、上传、用量),JSON 下载(`internal/export`)。
- 管理台对应入口 + 审计记录 `me.export`。

### 2.4 个人权利:删除权(PIPL §47)
- 用户硬删除:`DELETE /api/admin/users/{id}`(级联清理会话/记忆/成员关系,审计留痕)。
- 记忆生命周期:软弃用 → `DREAMING_PURGE_AFTER`(默认 30 天)清除。
- 上传文件删除:`DELETE /api/me/uploads/{id}`。
- **部署方义务**:对外承诺的删除时限需与备份保留期一致 —— 平台无内置备份,部署方若自建 `pg_dump` 备份,须在备份策略中同步处理删除请求(见 §4)。

### 2.5 安全防护(PIPL §51)
- 密码 bcrypt;会话 token SHA-256 哈希存储;登录节流(5 次/15 分钟锁定)。
- 团队 LLM 密钥与入站 webhook 密钥 **AES-256-GCM 静态加密**(`SECRETS_MASTER_KEY`,`internal/secrets`)。
- 审计日志 append-only(`internal/audit`);PII 脱敏(`internal/redact`)。
- RBAC:平台 admin / 团队 owner>admin>member 三角色;SSO(OIDC,兼容钉钉/企业微信/飞书)。
- 出站通知 HMAC 签名(`WEBHOOK_SIGNING_SECRET`)与 SSRF 防护;入站触发签名 + 时间窗 + nonce 防重放。

### 2.6 委托处理(PIPL §21)
- 对话内容发送至所配置 LLM 厂商 = 委托处理。**部署方义务**:与厂商签订数据处理协议(DPA),或在《隐私政策》中如实告知。
- 平台本身的处理者角色:自托管部署下平台为部署方工具,部署方为控制者。

### 2.7 安全事件(报告义务, PIPL §57)
- 审计轨迹 + request-id 关联日志 + `/metrics` 可支撑事件溯源。
- **部署方义务**:建立应急预案(账号锁定、密钥轮换、下线入口),并按规定向监管与个人报告。

## 3. 数据保留现状(需部署方决策)

| 数据 | 默认保留 | 说明 |
|---|---|---|
| 会话/消息/run | **永久**(无自动过期) | 建议按业务需要启用定期清理或导出归档 |
| 记忆 | 软弃用 + 30 天清除(可配) | `DREAMING_PURGE_AFTER` |
| 审计日志 | 永久 | 等保要求留存时长由部署方决定 |
| 用量 | 永久 | 按自然月聚合 |
| 入站 nonce | 6 分钟 TTL | 自动清理 |

**建议**:为满足"保存期限最小化"与等保留存之间的平衡,部署方可在运维层面(§4)实现对话保留策略,例如每月归档并删除超过 N 个月的会话(`DELETE FROM sessions WHERE created_at < ...` 前先导出),或联系社区评估官方保留策略开关。

## 4. 运维层配套(部署方实施)

- **备份与恢复**:建议 `pg_dump` 定时备份 + 恢复演练;备份副本须加密存放。注意删除权与备份保留期的衔接。
- **保留策略**:按 §3 规划会话/审计/用量的留存周期与归档。
- **审计查阅**:管理台 `/admin/platform/audit` 或 `GET /api/admin/audit`。
- **最小权限**:`query_db` 只读账号;沙箱隔离(off/local/docker);`SANDBOX_LOCAL_EXEC=false`。

## 5. 结论

平台侧已将 PIPL 的主要**技术**义务落地(告知面除外):导出权、删除权、审计、静态加密、访问控制、最小化读取、脱敏。剩余为**组织义务**:隐私政策公示、DPA、保留策略、备份衔接、应急预案 —— 这些属于部署方必须自行完成的治理动作。等保三级最常见的整改项(MFA、行级安全 RLS、备份工具)尚未内置,见 `docs/enterprise-readiness-2026-08.md` 的"仍缺"清单。
